# Passkey recovery: design

Status: accepted · Tracks: [#44](https://github.com/anuraggdubey/Tap-Pay/issues/44) (design), [#46](https://github.com/anuraggdubey/Tap-Pay/issues/46) (crypto, storage, restore), [#45](https://github.com/anuraggdubey/Tap-Pay/issues/45) (Settings UI)

## Goal

A user who created a device wallet can **optionally** link a passkey so they can recover the same wallet on a new phone without the 12-word recovery phrase. The recovery phrase stays the primary backup.

## Non-goals

- The passkey is **never** the wallet key. The key is generated on the device and held in the Android Keystore, exactly as today (#19, #20).
- No passkey login, no passkey-derived signing, no custody. Passkeys were removed as the primary wallet because the key was derived from an unstable relying party with no device gate. This design does not bring that back.

## Overview

```
LINK (existing device wallet)
  phone auth -> read phrase  -> passkey create/get with PRF -> AES-GCM encrypt
             -> wallet signs "put" proof -> upload ciphertext blob

RECOVER (new device, no wallet)
  passkey get with PRF (discoverable credential) -> credential id + PRF secret
             -> fetch blob by credential id -> AES-GCM decrypt -> verify address
             -> import into this device's Keystore (same path as phrase restore)
```

## Encryption scheme

| Item | Choice |
|:-----|:-------|
| Secret source | WebAuthn **PRF** extension output of the platform passkey (32 bytes). Never exported, never stored. |
| PRF input | Fixed salt `SHA-256("tappay/passkey-recovery/v1/prf-salt")` |
| Key derivation | HKDF-SHA-256, `ikm` = PRF output, `salt` = credential id bytes, `info` = `"tappay/passkey-recovery/v1/aes-gcm-key"`, 32 bytes |
| Cipher | AES-256-GCM, random 96-bit nonce per blob |
| Associated data | `"tappay-passkey-recovery\|v1\|<credentialId>\|<walletAddress>"` so a blob cannot be moved to another credential or wallet |
| Plaintext | JSON `{"t":"phrase"\|"key","v":"<secret>"}` (phrase for normal wallets, raw key for imported wallets) |
| Library | `@noble/ciphers` and `@noble/hashes`. No hand-rolled crypto. |

The blob is useless without the passkey: the AES key exists only while the authenticator answers the PRF request, which requires the user's fingerprint, face or screen lock.

Wrong passkey, tampered ciphertext, wrong credential, swapped wallet address or unsupported version all fail closed with the same generic error. No partial key material is ever returned.

## Relying party (RP) domain

The passkey is bound to a **relying party id**, and the credential only works for that id. Requirements:

- It must be an **owned, stable production domain**. Never a preview, throwaway or third-party hosting domain (this was the original bug).
- Android needs Digital Asset Links: serve `https://<rp-id>/.well-known/assetlinks.json` granting `delegate_permission/common.get_login_creds` to package `com.tappay` and the SHA-256 fingerprints of the **release** signing certificate (and the debug one for development builds).
- Changing the RP id later orphans every existing passkey. Pick it once.

The id is configured in `src/config/passkey.ts` (`PASSKEY_RP_ID`). It ships **empty**, and passkey recovery stays hidden and disabled until the owner sets it and publishes `assetlinks.json`.

## Where the blob lives

Decision: a **Supabase table written and read through an Edge Function** (`passkey-recovery`), not a device or cloud keystore.

Why: recovery has to work on a *new* device with no wallet and no local data, and Android has no keystore that reliably syncs arbitrary app data. A server row keyed by credential id works on any device the passkey syncs to.

| Aspect | Design |
|:-------|:-------|
| Table | `passkey_recovery_blobs(credential_id, wallet_address, ciphertext, nonce, version, ...)`. Row Level Security is on and no client role has access; only the Edge Function (service role) reads or writes. |
| Write (`put`) | Gated by a **wallet signature** over `credential`, `wallet`, `digest` of the blob and a timestamp (5 minute window). The server recovers the signer and checks it matches the wallet. One blob per wallet; linking again replaces the old one. |
| Delete | Same signature gate, and only for the wallet that owns the row. |
| Read (`get`) | By credential id only, because the new device has no wallet to sign with. The credential id is a random value generated by the authenticator. Reads are **rate-limited** per client and per credential, and responses for unknown ids look the same as any other failure. |
| What is stored | Ciphertext, nonce, credential id, wallet address, version, timestamps. No keys, no phrase, no PRF output. |

### Threat model

| Threat | Outcome |
|:-------|:--------|
| Database breach | Attacker gets ciphertext and wallet addresses. Without the passkey's PRF secret the ciphertext cannot be decrypted. Addresses are already public on-chain. |
| Server operator reads the blob | Same as a breach. The server never sees the key or the PRF secret. |
| Attacker guesses credential ids to fetch blobs | Ids are random and long, reads are rate-limited, and a fetched blob is still undecryptable. |
| Attacker overwrites or deletes someone's blob | Needs a valid wallet signature for that wallet. Replay is limited to the 5 minute window and is idempotent. |
| Lost phone with unlocked screen | Linking, removing and recovering all require device authentication; the passkey needs its own user verification. |
| Passkey provider account compromised | The attacker can decrypt the blob if they also reach the server blob by credential id. This is the inherent trade-off of passkey recovery, which is why it is **opt-in**, explained clearly, and the phrase remains the primary backup. |
| Malware reading memory | Out of scope. The decrypted secret is kept only for the duration of the operation and cleared afterwards (JavaScript cannot guarantee zeroization, so this is best effort). |
| Authenticator without PRF | Linking is refused with a clear message. No weaker fallback is offered. |

## Invariants kept from #11

- The decrypted phrase or key is never shown, copied, logged or put in AsyncStorage.
- One wallet per device: recovery is refused when a wallet already exists, linking is refused when none exists.
- Every action that touches the secret needs device authentication.
- Linking is opt-in. The UI says plainly that the recovery phrase is still the primary backup.
